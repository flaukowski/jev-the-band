# Architecture and recommended workflow

Updated 2026-09-20 for v0.5. See [Musical architecture](MUSICAL-ARCHITECTURE.md) for independently sized phrases, dedicated solos, queued themes, the sonic director, polyphony, instrument-specific rigs and global engineer. Earlier template behavior and its audit are preserved in the design history and `COMPOSITION-AUDIT.md`.

## Live musical decisions

Jev uses `POST https://openrouter.ai/api/alpha/decisions` with `typesafe/jev-1.13`. Its typed choice primitive returns probabilities, not free-form text or audio. A persona is an independent request context and application-owned musical memory, not a separate model deployment. No chat model substitutes for Jev's performance decisions. The separately labeled sonic director uses one structured OpenRouter chat-completions request to propose a concept and section map before Jev starts. Its validated request/result and reported cost are exposed separately; failure falls back transparently to the user's original prompt.

`server/composer.ts` first requests a phrase plan: action, tonal center, scale color, register, intent, contour, dynamics, attack count, initial rest, keyboard patches, bar timbre and tempo/harmony/ending proposals. A separate rig decision sees the chosen musical plan and selects every pedal independently for each bar. Then it requests one musical attack at a time. Each attack sees all of its accepted predecessors before choosing the next pitch, time to the next attack, held duration, velocity and articulation. A guitar attack includes a bend choice. Keyboard hands choose how many voices to use and each voice's actual MIDI pitch. Guitar chord modes choose each string pitch plus strum timing. Drums use a separate composer: an elected quarter/eighth/triplet/sixteenth grid, with kick, snare/tom, cymbal and velocity decisions at every position across both bars. There is no automatically inserted backbeat or chord.

The live renderer does **not** call the procedural score compiler. There is no rhythm-family selection, scale-anchor interpolation, automatic solo run, chord voicing, bass root/fifth pattern or motif transform in the live path. The model receives semantic descriptions of pitches (tonal function and distance from its previous note) to make bounded choices intelligible. Registers, note ranges and per-attack limits are declared instrument capabilities, not prerecorded phrases.

Creative note fields sample the model's own probabilities: temperature 0.7 and top probability mass 0.85, using a reproducible seed. Settled/releasing passages use temperature 0.35 and retain provider timing. A top option with probability at least 0.85 is retained unless it duplicates a key already selected for that hand; hand voices sample without replacement from nonzero probabilities. Planning decisions, rest/play and keyboard hand counts retain the provider's selected choice. Raw answers remain under `Trace.answers`; sampled/applied answers remain separately under `Trace.appliedAnswers`, with `selectionMethod`. Every sounded event carries `provenance.traceId` and `provenance.slot`. The next request sees the actually accepted notes, including sampled choices. This is model-guided probability sampling, not a claim that every played choice was the provider's argmax.

## Timing and listening

- Startup optionally creates the director brief (25-second timeout), then Jev chooses the opening from a neutral host context. The opener receives seven seconds of planning runway, bootstrap tonic/mode, concept and current section instructions. Recent opener history avoids a fixed bass-first bias without a mandatory round robin.
- Players enter one at a time. A fair oldest-due rotation admits one fresh musical idea per boundary. Each player chooses a 2/4/6/8/12-bar phrase independently, delivered as newly composed two-bar chunks. All committed phrases continue composing in parallel at each boundary, retaining their own motif and direction. Unselected accompaniment can repeat its accepted notes. A user-queued theme is the explicit exception permitting all four players to begin new ideas together.
- The first joining player begins planning 250 ms after the opener starts. Steady-state preparation starts up to two seconds before the preceding chunk, giving additional runway for sequential note decisions. The planner exposes peer note onsets only through actual current time minus 180 ms, clips held duration to elapsed sounding time, and excludes private peer intentions and unplayed scores, including queued frames. Only already-audible pedal states are included. Each successive attack call refreshes that cutoff against the same room snapshot. Private own-plan memory may include the player's unplayed notes. Rig decisions run concurrently with notes after the shared musical plan, and acceptance requires both.
- Lux makes its own independent call from heard notes. It never reads an unperformed musical draft.
- Patch makes at most one additional call on alternate phrase rounds when a reference browser has supplied actual channel measurements within ten seconds. It sees performed context and current mix, never future peer notes. Its accepted mix is scheduled in the next frame; absence/failure holds the prior mix.
- Jev's questions within one call are independent. Sequential attack calls allow melodic continuity; simultaneous chord voices still share one state and do not see each other's new choices.
- Web Audio uses server timestamps, a 25 ms scheduler poll and 180 ms lookahead. HTTP requests never schedule individual notes at their sounding instant. Visual animation follows performed note timing, without model calls.

Musicians use symbolic hearing, not acoustic perception. Patch receives numeric Web Audio RMS/peak readings, not uploaded audio. The clock delivers eight-beat chunks; a musical phrase can span several chunks independently of its peers. Arbitrary-time boundaries, long-term motif callbacks and continuous interaction remain future extensions.

## Declarative events and constraints

A `Frame` contains time, BPM, shared harmonic reference, `Part[]`, lighting and ending status. A part includes source, musical solo state, continuation status, optional `phraseFormat: events-v1`, tonal intention and explicit notes:

```json
{"beat":1.5,"duration":0.3333333333333333,"midi":62,"velocity":0.66,"hand":"right","patch":"rhodes","provenance":{"traceId":"provider-call-trace","slot":"right0"}}
```

A plan selects 4/6/8/10/12 attacks; keys allow at most eight attacks with up to five notes per hand. Intervals include 1/8 beat (32nds), 1/6, 1/5, 1/4, 1/3, 1/2, 2/3, dotted values and long notes. Spacing and held duration are separate choices, so gaps and overlap are explicit. The phrase has eight beats, at most 128 notes, and MIDI bounds 24–96, with narrower model-selected instrumental registers. Drums have their own two-bar event budget; they do not use the melodic attack limit. No score gate crosses the boundary; struck percussion recordings may naturally ring across it. Five-finger validation counts sustained overlap in each keyboard hand. Duplicate simultaneous attacks are collapsed. Rejected events are noted in the trace; the validator never invents replacement pitches or accompaniment.

A completed live composition is accepted atomically before its deadline. An HTTP/validation failure or missed deadline retains the previous actual events with fallback provenance; an instrument without a previous part rests. A failed solo continuation rests and clears solo status instead of repeating the old lead. Budget checks reserve the maximum next composition cost before beginning it. The default server request cap is 6,000 per jam, with a hard ten-minute lifetime and bounded memory (180 traces/eight frames). A lower configured cap can end a jam earlier. There are no unbounded retries.

## Musical evolution and ending

Live plans can choose a different register, mode and tonic per player, with common heard harmony as an anchor. Jev selects a diatonic, blues or chromatic palette. Chord textures and release-ending targets offer pitches from the chosen chord quality; the model chooses the actual notes. A player can make a chromatic approach, a modal contrast or a new melody when that vocabulary is selected. A shared tempo impulse stays within 1.2% per frame and ±10% of the initial tempo. Shared tonic proposals require two recent musicians' matching votes and a dwell period. They change the reference for future decisions; continuing live parts are not rewritten or transposed by the coordinator.

Solos are musical roles, independent of listener mixer solo. Multiple players can retain solo status. The model must write its actual melody and its ending; the app does not fabricate a lead from an arpeggio preset. Holding becomes unavailable after three identical own updates. Waiting for another player does not count. Memory compares actual scores, not action labels. After three identical own compositions, the next monophonic second attack must choose a different pitch from the prior second note, inside its selected palette; the opening anchor remains free to stay. Own direction, notes and heard peers guide development. Two consecutive build/peak updates require settle/release/space next.

Ending pressure rises after five minutes. Two recent ending votes can end the jam; the hard deadline always applies. Near the deadline the composer is told to resolve, but live notes are not rewritten into a canned final tonic. The demo retains its procedural final landing. Technical freshness checks and timing tests do not certify musical quality.

### Longer solos and queued themes

Guitar and keys enter a dedicated Jev solo plan, with an 8–32-bar duration sampled from its mood-conditioned probabilities, statement/development/resolution memory, and fresh note decisions for every two-bar chunk. Lead attacks must span both bars, vary pitches and repeated timing, and release the previous lead at the next attack; keyboard left-hand accompaniment can sustain. A solo opportunity becomes compulsory around 180 seconds without a new solo, subject to enough remaining jam time and successful provider calls. These constraints improve the available composition behavior; they are not a listening-quality guarantee.

The live prompt box queues up to four themes. Each gets a fresh optional LLM brief, using `openai/gpt-5.6-luna` by default. An eight-bar lead-in starts at the next two-bar boundary; later queued themes are spaced at least eight bars apart. At the target boundary all musicians receive the new theme and reset phrase/solo commitments while still hearing only performed peer notes. The room, request budget and ten-minute clock continue. A late or failed director falls back to the supplied theme text.

## Sound, rigs and stage

162 locally bundled recordings cover Karoryfer guitar/bass, piano and VCSL drum accents. Samples are individual notes, never loops. The manifest pins source commits and hashes. Other keyboard voices and selected drums use synthesis; missing recordings disclose a synthesis fallback. Sampled guitar offers dynamics, alternate takes and articulations, with per-note bends/slides/vibrato.

Each instrument owns an independent chain: note/envelope filter → RMS-matched drive worklet → wah and body/cabinet tone → chorus/delay/reverb → musical focus → soft-knee channel compressor → reference meter → Patch balance trim → listener fader/pan/meter → global room/glue compression → protected master. Drive measures only its own clean and saturated signal, targets slightly below clean RMS, smooths gain and protects the first transient. Drive has no cross-player gain detector or makeup boost. Beat-0/beat-4 pedal cues are clock-scheduled and retain trace IDs. Continuing players repeat the accepted timeline until their next turn. Kit's rig excludes wah, envelope filtering, chorus and tremolo, with low saturation/echo/room strengths; bass and keys also have role-specific modulation/wet levels. Faders, mute, multiple listening solos, pedal overrides, manual master mode and camera controls remain local to the viewer.

Starting a live jam marks that browser as a reference; an authorized host can select one after joining. It posts four channel RMS/peak pairs every 2.5 seconds to the protected `/api/room/levels`, with validated finite bounds and room identity. These readings precede listening faders/mutes/solos but include the reference browser's pedal/tone colors. The server uses only fresh data and rate-limits acceptance to 750 ms. This prototype relies on the host using one reference browser; it has no reference lease. Patch moves at most 1 dB per channel per update, within ±6 dB, does not chase silent channels or boost hot peaks, and selects bounded reverb/compression. Manual mode bypasses those trims and uses saved master settings. No audio is uploaded or analyzed by a multimodal model.

The audience sound has a separate bus feeding the master mix. Patch classifies the performed mood and chooses audience attenuation in its existing request; local controls can mute the audience, disable reactions, or set mood/level manually. Beds crossfade and occasional reactions are spaced apart. The current fallback is explicitly labeled procedural room noise and applause. A bounded ElevenLabs generation script and reviewed, hashed local sample-bank loader are implemented; no generated crowd recordings are bundled yet. See [audience research and workflow](AUDIENCE.md).

The stage includes the banner, performers, crowd, rigs, camera orbit/presets and timestamp-driven instrument animation. Reduced-motion controls remain. Viewers share one server performance; adding an audience does not create model calls.

## Demo and verification workflow

The instrument demo makes zero provider calls. `shared/score.ts` retains its three motifs, rhythm templates and procedural arrangement for renderer checks. Its title is a label, not a semantically interpreted composition prompt. Live Jev is the default when the host has a key; the running room's actual mode is always displayed.

1. Run deterministic constraints, causality, provenance, failure and duration checks with `npm run check`.
2. Use muted browser tests for real audio levels, isolated rigs, samples, rendered controls and spectator behavior.
3. Explicit paid diagnostics: `smoke:live` checks five persona plans; `smoke:performance` caps at 240 calls/90 seconds; `audit:prompts` compares two isolated openings, at most 70 calls each. `audit:groove` tests three isolated actual chord/drum compositions, capped at 28 calls. None run in CI or replace the audience room.
4. Listen to a fresh live session and inspect raw/applied choices. Evaluate continuity, melodic identity, space, interaction and dynamics separately from mechanical checks.
5. Record taste changes and user corrections in the prompt and decision logs. Public hosting still requires a dedicated key, protected controller, shared audience design and an explicit publishing action.
